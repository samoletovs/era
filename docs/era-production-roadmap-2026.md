**Status:** Active plan
**Owner:** Sam

**Scope:** Latvia first → Estonia + Lithuania after

> **Reframe.** era stops being a "lab experiment" and becomes a system real Latvian SIAs can rely on day-to-day. No selling, no pricing — just reliability, compliance, and depth on Latvia. EE + LT come *after* LV is solid.

---

## What "production-ready" means for era

A money system is production-ready when **all five** are true:

1. **Correct** — every posted entry survives audit; no silent rounding bugs; idempotency on every agent action.
2. **Compliant** — meets current Latvian regulation (Cabinet Reg 775, VAT Act, **PEPPOL B2G mandatory since Jan 1 2026**, gada pārskats, payroll).
3. **Observable** — every action traceable end-to-end; cost and errors visible without SSH'ing into anything.
4. **Resilient** — survives Cosmos throttling, cold starts, OpenAI rate limits, and at least one full restore drill.
5. **Trustworthy to a non-developer** — explainability, undo, sane error messages, no naked stack traces.

Today era is ~3/5: correct (mostly), partly compliant (PEPPOL gap, VID submission gap), weak observability, untested resilience, low explainability.

## Critical compliance flag

**PEPPOL B2G e-invoicing has been mandatory in Latvia since 1 January 2026.** As of plan creation (2026-05-10) era is **4+ months past this deadline** for any SIA invoicing the Latvian state. Moves to Phase 1.

## Phase 1 — Reliability & compliance foundation (Weeks 1–3)

Make era *safe* to put real Latvian SIA data into.

### Reliability

- [x] **HTTP integration suite (`tests/integration/`)** — backend tests via supertest + an in-memory Cosmos fake. See [`docs/integration-tests.md`](integration-tests.md). Minimum 7 paths: (1) create→post→pay invoice ✅; (2) month-end run ✅; (3) year-end + period close ✅; (4) VAT declaration generation ✅; (5) chat-driven invoice creation ✅; (6) FX revaluation ✅; (7) bank-rec import ✅. _Playwright UI smoke is deferred — backend correctness is the priority._
- [x] **Idempotency keys** on every `agent-tools.ts` mutation. Pattern: tool calls accept optional `clientToken` (auto-injected into all 13 mutation tool schemas via `MUTATION_TOOLS` set); the agent dispatcher (`executeTool`) deduplicates against the Cosmos `idempotency` container (PK `/companyId`, 7-day TTL). Prevents the "agent retries → posts twice" class of bug. Complementary to the existing HTTP `X-Idempotency-Key` middleware (in-memory, per-replica). 12 unit tests + 3 integration scenarios cover hit/miss/conflict/no-token paths.
- [x] **App Insights + OpenTelemetry** — `@azure/monitor-opentelemetry` distro bootstrapped in `src/backend/observability.ts` with top-level `await import()` so it registers BEFORE any HTTP/Cosmos/OpenAI module is evaluated (the docs are explicit that ordering matters for auto-instrumentation). Activated only when `APPLICATIONINSIGHTS_CONNECTION_STRING` is set, so local dev and tests boot as silent no-ops. Manual spans wrap the high-value boundaries: `agent.chat` around the chat handler with attributes (`era.user_id`, `era.company_id`, `era.chat.message_length`, `era.chat.history_length`); `agent.tool.<name>` around every tool execution with attributes for the tool name, mutation flag, idempotency cache hit/miss, and client token. Trace IDs flow through to the data layer — `BusinessEvent` and `JournalEntry` both gained an optional `traceId` field that's stamped at write time via `currentTraceId()`. Result: a single click on a chat error in App Insights drills straight through to the tool span, the GL row it produced, and the audit-log event behind it. 6 unit tests in `tests/unit/observability.test.ts` cover the no-op tracer + invalid-trace handling; 5 in `tests/unit/events-trace.test.ts` cover stamping precedence (active span → input override → omitted when undefined). Bicep already wires the connection string into the Container App env, so deployment is a no-op infrastructure-side.
- [x] **Cold-start fix** — Container Apps `minReplicas: 1` on the API revision (`infrastructure/main.bicep`, ~€15/mo, within the lab's monthly Azure credit). Eliminates the warm-up latency on the first request after idle and ensures `/health` responds within the 3s probe budget.
- [x] **Cosmos DB restore drill** — DR runbook + reconciliation tooling shipped. The Cosmos account currently runs on the default Periodic backup mode; the runbook ([`docs/dr-runbook.md`](dr-runbook.md)) lays out the one-way migration to `Continuous7Days` (free tier, 7-day PITR window, sufficient for our detection horizon) along with the exact `az cosmosdb restore` invocation and the RBAC re-assignment caveat. The reconciliation primitive lives in [`src/backend/services/restore-reconciliation.ts`](../src/backend/services/restore-reconciliation.ts) — it pulls posted `JournalEntry` rows from the primary and restored Cosmos accounts for one company, then proves the trial balance ties out per `(accountCode, period)` cell, with float-noise tolerance at €0.005 and a 0-cent reconciliation budget. Driven by a small CLI ([`scripts/verify-restore.ts`](../scripts/verify-restore.ts)) that exits 0/1/2 for use in drill scripts. 12 unit tests cover happy path, missing entries, extra entries, per-account drift, draft-status filtering, and float rounding. The infra migration itself is held back as one-way and human-reviewed; the runbook captures every step Sam takes when he flips it.
- [x] **Health endpoint** (`/health`) — extracted into `services/health.ts` and exposed at `GET /health` returning `{ status, version, timestamp, checks: { api, database, openai }, errors? }`. Each dependency check is wrapped in a 3s timeout via `Promise.race`; failures are aggregated rather than thrown, and the endpoint replies `200` on healthy / `503` on degraded. Cosmos is probed via `getDatabaseAccount()`; OpenAI is validated via env-var presence + URL parse (no token-spending API call). Storage is intentionally not probed — the SDK is in `package.json` but not used at runtime, so probing it would falsely fail. The shared cross-repo monitor (`.github/scripts/nauro-monitor.py`) was extended with an optional `health_path` field on each manifest entry; era opts in via `"health_path": "/health"` in `workspace-manifest.json`. When set, the monitor parses the JSON body and surfaces individual unhealthy dependencies (e.g. `degraded deps: openai`) instead of the binary 200/non-200 it does for static SPAs. 7 unit tests (`tests/unit/health.test.ts`) cover all-healthy, cosmos-down, missing-endpoint, missing-key, malformed-URL, multi-failure aggregation, and timeout paths.

### Compliance (legal-blocker P0)

- [x] **PEPPOL BIS Billing 3.0 — autonomous slice shipped (vendor wiring is the only remaining step).** Already overdue for B2G; B2B mandatory Jan 1 2028. New domain types `PeppolOutboxEntry` / `PeppolOutboxStatus` ([`src/shared/types/entities.ts`](../src/shared/types/entities.ts)) ride on the existing `documents` Cosmos container with a `docType: 'peppol-outbox'` discriminator (no new infra/Bicep, no migration risk). [`src/backend/services/peppol/ubl-builder.ts`](../src/backend/services/peppol/ubl-builder.ts) emits **UBL 2.1 / BIS Billing 3.0** XML — `CustomizationID urn:cen.eu:en16931:2017#compliant#urn:fdc:peppol.eu:2017:poacc:billing:3.0`, `ProfileID urn:fdc:peppol.eu:2017:poacc:billing:01:1.0`, `InvoiceTypeCode 380`, deterministic tax-subtotal aggregation (positive rate → "S", zero → "Z"), Latvian endpoint schemes (`0218` registration number preferred, `9925` VAT fallback) — using only string templates + `escapeXml()` so output is golden-testable. [`src/backend/services/peppol/access-point.ts`](../src/backend/services/peppol/access-point.ts) defines the `PeppolAccessPoint` interface plus `NoOpAccessPoint` (returns `NOT_CONFIGURED` non-retriable) and `MockAccessPoint` (deterministic IDs, ring buffer) so the orchestrator is testable without a vendor account. [`src/backend/services/peppol/dispatcher.ts`](../src/backend/services/peppol/dispatcher.ts) glues invoice + company + customer into the UBL document, persists `pending`, calls the Access Point, and persists the final outcome (`sent` with `provider`/`providerMessageId`/`sentAt` or `failed` with mapped `lastError.code`). HTTP routes added to [`src/backend/api/router.ts`](../src/backend/api/router.ts): `POST /companies/:companyId/invoices/:invoiceId/peppol` (dispatch), `GET /companies/:companyId/invoices/:invoiceId/peppol/preview` (returns UBL without persisting — useful for agent inspection), `GET /companies/:companyId/peppol/outbox?status=` (list with optional filter). Provider chosen via `process.env.PEPPOL_PROVIDER` (`mock` for local dev, unset → NoOp). 32 new unit tests ([`tests/unit/peppol-ubl.test.ts`](../tests/unit/peppol-ubl.test.ts)) cover the full UBL skeleton, multi-rate aggregation/sorting, Latvian endpoint derivation, validation rejections (purchase invoices, missing country, empty lines), and the dispatcher contract. **Plugging in a real Access Point (Storecove/Tickstar) is now ~50 LoC: implement `PeppolAccessPoint.send()` + register it in `selectPeppolAccessPoint`.** No SMP/SML registration is hard-coded; the Access Point owns that.
- [x] **VID / EDS submission — autonomous slice shipped (live EDS endpoint is the only remaining step).** New domain types `VidSubmission` / `VidSubmissionStatus` / `VidSubmissionAttempt` ([`src/shared/types/entities.ts`](../src/shared/types/entities.ts)) again ride on the `documents` container under `docType: 'vid-submission'`. [`src/backend/services/vid/submit.ts`](../src/backend/services/vid/submit.ts) is a single self-contained module: `vatDeclarationToVidXml()` emits a VID-shape declaration document (namespace `urn:lv:vid:eds:pvn:1.0`, Header/Totals/Lines, two-decimal money, type+rate per line); the `VidClient` interface plus `NoOpVidClient` / `MockVidClient` lets the orchestrator be exercised without a VID account; `submitVidDeclaration()` runs the queued → submitting → accepted/rejected/failed state machine; `retrySubmission()` enforces the legal transitions (`accepted` is terminal-success, `rejected` is terminal-fail, `failed` is retriable up to `maxAttempts`); `computeNextAttemptAt()` uses exponential backoff (`base * 2^(attempts-1)`, default base 60s, default max 5 attempts). Errors are mapped to a closed enum (`AUTH | INVALID | NETWORK | NOT_CONFIGURED | UNKNOWN`) with a `retriable` flag — only retriable errors arm `nextAttemptAt`. HTTP routes: `POST /companies/:companyId/vid/submissions` (body `{kind, year, month?}` — generates declaration via the existing `generateVatDeclaration`, builds XML, calls client, persists), `POST /companies/:companyId/vid/submissions/:id/retry`, `GET /companies/:companyId/vid/submissions?status=&period=`. Provider chosen via `process.env.VID_PROVIDER`. 22 new unit tests ([`tests/unit/vid-submit.test.ts`](../tests/unit/vid-submit.test.ts)) cover XML structure/escaping/empty-lines fallback, the backoff schedule (60→120→240→480), all three terminal/retriable outcomes, the retry refusal rules, and `MockVidClient` deterministic receipts. **Wiring the live EDS HTTPS endpoint is now ~50 LoC: implement `VidClient.submit()` against the real API + register it in `selectVidClient`.** Closes the 4-month-old "era generates but doesn't submit" gap on the orchestration side.
- [x] **Annual report (`Gada pārskats`) polish — formatter, PDF, and sign-off lock shipped.** [`src/backend/services/annual-report-pdf.ts`](../src/backend/services/annual-report-pdf.ts) provides three layers: (1) `formatAnnualReport(report, {locale, approval})` returns a presentation-ready `FormattedAnnualReport` with Latvian (default) or English labels, balance-sheet equation rows, P&L cost lines rendered as negatives so the visual stack matches statutory presentation, total-row marking for Gross profit / Profit before tax / Net profit, and a `lockBanner` when an approval is locked or submitted; (2) `renderAnnualReportPdf(formatted)` produces a PDF via the already-installed PDFKit (header → balance sheet → P&L → signature page → statutory footer with snapshot hash); (3) a small lock state machine — `AnnualReportApproval` ([`src/shared/types/entities.ts`](../src/shared/types/entities.ts), `docType: 'annual-report-approval'`) plus `lockAnnualReport` / `unlockAnnualReport` / `markSubmittedToVid` and a `LockError` with stable `code`s. Locking refuses re-locking, missing signatory name/role, or a fiscal-year mismatch between approval and report; unlocking refuses if status is `submitted` (it's been sent to VID, no take-backs); a submission can only be marked from `locked`. `computeSnapshotHash()` is an FNV-1a hash over the canonical numbers only (Balance Sheet + P&L; ignores company name and locale) — drift in the underlying ledger between lock and re-render shows up as a hash change. HTTP routes: `GET /companies/:companyId/reports/annual/:year/pdf` (renders PDF, includes lock banner when applicable), `GET /.../approval` (returns the approval entity if any), `POST /.../lock` (body `{signatoryName, signatoryRole, signatoryRegistrationNumber?}`), `POST /.../unlock`. 22 new unit tests ([`tests/unit/annual-report-pdf.test.ts`](../tests/unit/annual-report-pdf.test.ts)) cover formatter (LV/EN, equation, sign convention, lock banner), snapshot determinism (drift on number change, ignores company name, 8-char hex), and the full lock/unlock/submit transition table. Tests use `expect(...).toThrowError(/.../)` against `error.message` (not `error.code`) — fixed early after a false-negative initial pass.
- [x] **Cabinet Regulation 775 audit** — every LV posting rule in [`src/shared/rules/lv.ts`](../src/shared/rules/lv.ts) now carries a `legalBasis: string[]` field with paragraph-level citations, backed by a new optional field on the `PostingRule` interface ([`src/shared/types/entities.ts`](../src/shared/types/entities.ts)). The audit also corrected a meaningful misdescription: the file header used to claim Reg 775 *is* "the Latvian Chart of Accounts," but Cabinet Regulation No. 775 of 22.12.2015 (likumi.lv id 278844) is in fact the *application rules* for the Annual Reports Law (Gada pārskatu likums) — it governs recognition, valuation, and presentation, not account numbering. The 4-digit codes era uses (2210 AR, 4220 AP, 4230 VAT payable, 5220/6420 FX, etc.) are commercial convention adopted as accounting policy under §29–§30, not regulatory mandate. Per-rule mapping: sales-invoice cites §50 (Net turnover), §51 (revenue definition), §52 (third-party VAT excluded from revenue), §53 (transfer-of-risks recognition), §156 (debtor balances based on supporting documents) plus VAT Law for output VAT; purchase-invoice cites §156 (creditor balances) plus VAT Law and the Annual Reports Law cost-classification schema; incoming/outgoing payment cite §156 (settlement); FX revaluation cites §38–§39 (reliable accounting estimates) and §105¹ (FX revaluation explicitly distinguished for CIT) plus the Annual Reports Law on foreign-currency monetary items. Findings and the methodology for extending this to future countries are written up in [`docs/lv-posting-rules-audit-2026.md`](lv-posting-rules-audit-2026.md), and the [`posting-rules` skill](../.github/skills/posting-rules/SKILL.md) was updated so future rules cite paragraphs in `legalBasis` rather than only naming the regulation in `source`. All 237 unit tests + 13 integration tests + lint + build pass; no test asserts the exact `PostingRule` shape, so the new optional field is non-breaking.

## Phase 2 — Trust & autonomy (Weeks 4–5)

Make the agent's actions **legible, reversible, proactive**.

- [x] **Explainability badge** on every JournalLine: `🤖 Agent · LV-rules-v1.2 · sales-invoice` → tooltip expands to rule version, source BusinessEvent ID, agent reasoning excerpt, "revert" button.
  - Done 2026-05-10. Five new optional fields on `JournalLine` (`postingRuleId`, `postingRuleVersion`, `postingRuleCountry`, `postingRuleDocumentType`, `agentReasoningExcerpt`); the posting-rule engine stamps them via a new `buildProvenance` helper inside `evaluateInvoiceRule` / `evaluatePaymentRule`. `GlPostings` renders a compact `🤖 LV-rules-v1` badge next to the account code; tooltip shows rule id, version, document type and the (≤280-char) agent-reasoning excerpt; the badge is a `<Link>` to `/audit/entry/{id}` whenever the parent journal entry id is known. Backward-compatible: hand-posted entries with no rule provenance simply render no badge. Revert is deferred to the "Reversibility" item.
- [x] **Audit trail page** `/audit/{eventId}` — full chain `ChatMessage → AgentAction → BusinessEvent → JournalEntry → JournalLine`. Data already exists; needs UI.
  - Done 2026-05-10. Pure-functional `assembleAuditChain` over an injected `AuditChainLoaders` interface (13 unit tests with mock loaders covering every degraded-data path) plus `defaultLoaders()` that wraps the real Cosmos containers. Two HTTP routes: `GET /companies/:companyId/audit/event/:eventId` (404 `AUDIT_EVENT_NOT_FOUND`) and `GET /companies/:companyId/audit/journal-entry/:entryId` (404 `AUDIT_ENTRY_NOT_FOUND`). One React page (`pages/Audit.tsx`) bound to both `/audit/event/:id` and `/audit/entry/:id`; renders chat-message panel, business-event card, the journal entry inside an embedded `GlPostings`, the source invoice or payment, and the posting-rule card with legal basis. Note: `AgentAction` is a defined type but never persisted, so the rendered chain is `ChatMessage → BusinessEvent → JournalEntry → source document → PostingRule`. Manual postings degrade gracefully — every loader swallows exceptions and returns `null`.
- [x] **Reversibility** — every AgentAction stores enough state for one-click revert (creates a counter-entry, not a delete).
  - Done 2026-05-10. The backend primitive (`reverseJournalEntry` in `services/ledger.ts`) already marked the original as `status: 'reversed'` and posted a counter-entry with flipped debits/credits — but it copied rule-provenance fields onto the counter (mis-claiming the reversal was rule-driven) and emitted `entry.reversed` *before* the counter existed. Fixed: provenance fields are stripped on the reversed lines, the counter is posted first, and the `entry.reversed` event now carries `reversalEntryId` + `reversalEntryNumber` so the audit chain can render the partner. Frontend: a "↩️ Revert this entry" button on the new audit page (with a `window.confirm` guard, in-place result banner, and link to the counter's audit page) plus an inline "Audit / ↩️ Revert" action pair on every row of the JournalEntries list. New integration test `09-reversal-audit.test.ts` exercises the full chain end-to-end: post a sales invoice, fetch the audit chain (asserts rule provenance is present), revert, verify the counter has flipped debits/credits and **no** rule provenance, verify the original is now `reversed`, verify the counter's audit chain has `rule: null` (sourceType `adjustment`), and verify a double-reversal is rejected. AgentAction itself is still not persisted — the chain we have (event + journal entry + lines + rule) is sufficient state because every rule-driven posting can be deterministically reversed by flipping debits/credits.
- [ ] **Proactive agent** — daily 09:00 LT cron: overdue invoices ≥ 3 → push; month within 3 days of close → "ready to close?"; FX drift > 10% → push; recurring template due → execute + push.
- [ ] **Telegram + email** notification channels; `notificationPreferences` on Company.
- [x] **Cleaner error surfacing** — Zod errors translated to user-readable Latvian/English; no naked stack traces in UI.
  - Done 2026-05-10. New shared bilingual catalog ([`src/shared/errors/catalog.ts`](../src/shared/errors/catalog.ts)) maps every error code the backend currently emits (`VAL-001`, `BIZ-001`, `AUTH-001/3/4`, `MIN_LINES`, `ALREADY_REVERSED`, `NOT_FOUND`, `RATE_LIMITED`, `SYS-001/2`, `AUDIT_*`, `PEPPOL_*`, `VID_*`, `ANNUAL_*`, plus the GLError codes from `services/ledger.ts`) to a Latvian + English message pair, and translates the common Zod issue codes (`invalid_type`, `too_small`, `too_big`, `invalid_format`, `invalid_enum_value`, `invalid_union`, `unrecognized_keys`, `custom`) so users no longer see "Expected string, received undefined" in the UI. Validation middleware now stamps each Zod issue's `code` alongside the `field`/`message` in the response envelope so the frontend translator can render a clean field-by-field summary even when the upstream Zod text is too technical. Frontend got an `ApiError` class that preserves `code` + `details` + `status` end-to-end and a `formatApiError(err, locale)` helper backed by the shared catalog; `apiFetch` now throws structured `ApiError` instead of bare `Error` strings, so 401/429 also carry codes (`AUTH-001` / `RATE_LIMITED`). Wired three demo surfaces — `pages/Audit.tsx` (also fixed a pre-existing bug where the audit page never rendered the chain because of a stale `ApiResponse<T>` envelope cast on top of `apiFetch`'s already-unwrapped data), `pages/JournalEntries.tsx` (revert-row alert), and `components/AiInput.tsx` (chat error). Backend got a top-level Express error-handler middleware ([`middleware/error-handler.ts`](../src/backend/middleware/error-handler.ts)) wired as the last `app.use(...)` in `index.ts`; it backstops anything that escapes per-route try/catch, reuses `safeError` so the response shape is identical to existing routes, and never leaks an internal stack trace to the client (verified by a unit test that asserts internal phrases are masked from the response body). Tests: 17 catalog tests cover bilingual coverage, missing-code fallback, Zod issue translation, multi-detail formatting (capped at 3 with localized "more"/"vēl" suffix), and GLError-code paths; 6 middleware tests cover GLError → 400, "not found" → 404, masked-stack → 500, and the `headersSent` delegation path. **Phase 2 status:** 4 of 6 done. Remaining: proactive cron, Telegram + email channels.

**Phase 2 done when:** every posted entry shows its provenance in 1 click; agent has executed at least one fully-autonomous month-end with push notification; one full revert tested end-to-end.
